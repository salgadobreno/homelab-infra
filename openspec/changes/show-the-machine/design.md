# Design

## Context

| Constraint | Detail |
|---|---|
| Serving | `buzaga.com.br`, `www.`, `k8s.` → traefik → the `site` Deployment; the hypervisor serves nothing |
| The page today | one `index.html`, ~2.7 KB, in a kustomize-generated ConfigMap |
| Available data | `k3s-server-1 Ready v1.36.3+k3s1 4 vCPU 6067388Ki`; `site Synced Healthy rev 842e3c6` |
| Disclosure | operator decision 2026-08-22: shapes, not addresses |
| Deployment path | commit and push; ArgoCD reconciles within its poll interval |
| The audience | someone who will not read this repository |

## Goals

- A visitor sees what is actually serving them, written from the cluster's own output.
- The page cannot be wrong and green at the same time.
- Nothing new runs in the cluster.

## Non-Goals

- Rendering at request time. See D1.
- A dashboard, metrics, or history. That is M7.
- Owning the page. This is a fragment that will later sit inside a `projects` section.

## Decisions

### D1: Static content generated by a command, not a renderer in the cluster

An earlier draft of this design had a sidecar running `kubectl` and writing a file nginx
served. It came from reading `config.yaml`'s "generated from live state" as "generated at
request time" — an escalation of the operator's actual requirement, which was that the
picture not be *drawn by hand* as `diagram.ascii` was.

The difference in cost is large and one-sided. A runtime renderer needs a ServiceAccount,
a Role, a RoleBinding, a second container in the pod, a staleness indicator on the page,
and a new failure mode where the renderer dies while nginx keeps serving. All of that to
keep current a page whose subject changes a few times a month.

Generated and committed, the page is content like every other page: it deploys the way
everything else deploys, and there is nothing new to secure or to watch.

*What the runtime version would have bought:* currency measured in seconds rather than in
commits. Nothing on this page is worth that.

### D2: Drift is a failing check, not a stale page

The objection to static content is real — a generated page goes stale exactly as a drawn
one does, which is how `diagram.ascii` came to name three technologies that do not exist.

`make diagram` regenerates from the cluster. `make check-diagram` regenerates into a
temporary file and compares it with what is committed, failing on any difference. So:

- the page can be wrong, but not wrong and green;
- the failure names what changed, because it is a diff;
- the fix is always the same single command.

This is the property the runtime renderer was reaching for, obtained for a script and a
`diff`.

*Consequence accepted:* this is the first check here that fails because the world moved
rather than because the repository did. `make check` stops being purely a statement about
this repository. That is the correct trade for a page whose entire purpose is to agree
with the world, but it is a change in what the suite means.

### D3: The generator must be deterministic, or the check is noise

A drift check is only usable if identical inputs give identical output. Sources of
spurious difference to suppress deliberately:

- **Timestamps and ages.** `4m12s` becomes a different string every run. Report a date at
  day granularity, or nothing.
- **Ordering.** `kubectl` output order is not guaranteed; sort explicitly.
- **Counts that flap.** A pod restarting during generation changes a ready count. Report
  desired state, not momentary state.
- **Anything ephemeral.** Pod name suffixes, resource versions, IPs — most of which the
  disclosure boundary already excludes.

**A fifth source turned up while building the generator, and it cannot be normalised —
it has to be left out.** ArgoCD's synced revision is the commit that contains this file.
Publishing it means every push changes what the page should say, so the drift check goes
red after each commit; and the fix — regenerate and commit — is itself a new commit, which
changes the value again. There is no fixpoint.

Normalising the revision away instead would let the page display a stale commit and stay
green, which is exactly what D2 forbids. So sync status and health are published and the
revision is not. **This also answers Open Question 3: the page cannot name the commit it
was generated from, for the same reason.** A value that changes *because* it was
committed cannot appear in a file whose correctness is a byte diff.

A generator that fails this makes `make check` fail at random, which trains the operator
to ignore it — the same way the three wrong checks in M2 trained trust in a green result
that meant nothing.

### D4: The disclosure boundary is an allow-list, enforced by a check

Operator decision: **shapes, not addresses.**

| Published | Withheld |
|---|---|
| node name, Ready state, kubelet version | node IP, hypervisor hostname |
| CPU and memory capacity | storage class, paths, volume names |
| workload names and desired counts | pod IPs, cluster IPs, pod name suffixes |
| ArgoCD sync status and health | account names, token IDs, the synced revision (D3) |
| image names and tags | anything about the tunnel or the hypervisor |

A deny-list would be wrong: it enumerates what is known sensitive today, against a
generator that will report whatever the cluster returns tomorrow. The check greps the
generated output for the *shapes* of forbidden values — anything matching an IPv4 address,
an absolute path, or the known account names — and fails on a match.

That check is the requirement. "Be careful what you print" is not enforceable.

### D5: Both halves, in different registers

What runs now is generated. What it replaced is not — the Compose stack is gone and
cannot be queried, so its description is content written once, from the record made in M4
before it was destroyed.

The two are labelled differently on the page. Presenting a remembered thing and a measured
thing in the same register is precisely the habit that made `diagram.ascii` credible for
as long as it was.

## Risks

| Risk | Mitigation |
|---|---|
| The generator is non-deterministic and `make check` fails at random | D3 names the sources; the reproducibility scenario is a spec requirement, tested by running it twice |
| A forbidden value reaches the page as the cluster grows | The check greps shapes, not known values, and runs in `make check` |
| The page is regenerated on a broken cluster and commits the breakage | The generator reports what it read; a rebuild in progress is visible in the diff rather than silently committed |
| `make check` now depends on the cluster being reachable | It already does — `check-site` talks to the API and distinguishes unreachable from broken |

2. ~~Where does the generated fragment live?~~ **Answered: a separate file,

   over a file that is 100% generated, and the generator never touches hand-written markup.

   cannot.** See the fixpoint argument in D3. Resolved 2026-08-22 while building the
   generator, not by preference.
