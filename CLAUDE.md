# CLAUDE.md

Guidance for Claude Code (claude.ai/code) working in this repository.

## What this repo is

Infrastructure-as-code for a single-host Proxmox VE homelab. Two goals, both real: run
a professional setup, and build hands-on fluency in Terraform, Kubernetes, and ArgoCD.
When they conflict, prefer the industry-standard choice over the homelab-clever one —
the operator needs to explain each decision in an interview.

Planning is done with OpenSpec (`openspec/`). Read `openspec/config.yaml` for the full
project context — hardware constraints, the address plan, storage tiers, and standing
decisions. It is the authoritative source and is kept current; this file is a summary.

## Layout

```
openspec/          OpenSpec planning: config.yaml, changes/, specs/
tofu/              OpenTofu root module — flat and unmodularised on purpose
scripts/           bootstrap.sh (toolchain), create-proxmox-token.sh (Proxmox API token)
Makefile           Operator console — every routine command lives here
LEARNINGS.md       Learning log, written after the fact (see protocol in the file)
```

## Operator console

Routine administrative commands belong in the `Makefile`, not in ad-hoc shell
invocations. `make help` lists them; `make status` gives a one-screen overview.

When reaching for a status or check command, **use the target if one exists, and add a
target if one does not.** The point is that the operator can run exactly what the agent
ran and see the same output. A command that only ever appears in a chat log is invisible.

Targets that need root are marked; the operator runs those in a real terminal.

`tofu/` stays flat until there is more than one node to abstract over. Extracting
modules is a deliberate later exercise, not an oversight.

## Workflow

Work is planned as OpenSpec changes and applied task by task:

```bash
openspec list --json                                  # active changes
openspec status  --change "<name>" --json             # artifact + task state
openspec instructions apply --change "<name>" --json  # apply context
openspec validate "<name>"
```

Scope every change as a thin end-to-end slice that ends in something demonstrable — a
URL that serves, a command that returns, a rebuild that completes. One change per
milestone, never one per layer. Two previous attempts at this project stalled because
they were structured layer-by-layer and produced nothing observable until the end.

## Toolchain

`scripts/bootstrap.sh` installs `tofu` and `kubectl` into `~/.local/bin` with pinned
versions and checksum verification. It is re-runnable and needs no root.

This host has **no passwordless sudo and no TTY** in agent sessions. Anything needing
root must be run by the operator in a real terminal — do not attempt `sudo` and do not
work around it. `qm`, `pct`, `pvesm`, and `pveum` live in `/usr/sbin` and need root.

Before invoking any tool, check `command -v` first. Do not run tools speculatively or
invent their output.

## Safety

This repo manages real hardware running a live Cloudflare tunnel.

- **Never run `tofu apply`, `tofu destroy`, `kubectl apply`, `helm upgrade`, or a
  destructive `qm`/`pct` command unless the operator explicitly asks for that specific
  action.** Produce a plan or diff and let them decide. Authorisation to work a change
  is not standing authorisation to apply every step in it.
- Never commit credentials, kubeconfigs, `*.tfstate`, or private keys. `.gitignore`
  covers these; verify with `git check-ignore` rather than assuming.
- `tofu/terraform.tfvars` holds the Proxmox API token. It is gitignored, mode 600, and
  generated by `scripts/create-proxmox-token.sh`.

## Known shortcuts

Recorded deliberately, with a milestone to fix each — do not mistake them for oversights
or silently "improve" them:

- The Proxmox API token is attached to `root@pam` with privilege separation off. A
  scoped `terraform@pve` user belongs to the secrets milestone.
- Terraform state is a local file. Remote state solves collaboration problems this
  single-operator project does not have.
- The Cloudflare tunnel token is visible in the `cloudflared` process arguments.
- There is no configuration-management layer, by design. Nodes are immutable; cloud-init
  bootstraps them and GitOps reconciles everything above the OS. Do not reintroduce
  Ansible without an explicit decision.
